## 1. The question
Greg's working belief: chalk CPT (captain) picks tend to miss (fail to pay off), so fading them is +EV. Nothing so far confirms or refutes that; last week's single showdown was ambiguous (see 5). Two goals:
1. **Accuracy first:** make showdown ownership estimates (CPT and FLEX separately) close to the real field's. Target, same spirit as classic: no "4% vs 40%" misses on the players that matter (players >= ~20% owned at CPT or FLEX).
2. **Then define "chalk captain" precisely and test it:** e.g. top-N owned CPT per slate; compare its outcomes (points, rank of the CPT among all players' CPT-scores, lineup finish) against its ownership. Be honest about sample size: only a handful of showdown slates have real results, and outcomes within one game are highly correlated. Prefer within-slate analysis that uses the thousands of real lineups per slate, and say plainly what one game can and cannot show.

## 2. What we did for CLASSIC (the method to mirror)
All in `scripts/ownership_model.py`, `scripts/fit_ownership_model.py`, `data/ownership_model_dk.json` (committed, DK classic only; Showdown and FD were deliberately left on the old heuristic).
1. Measured the old heuristic (`scripts/ownership_heuristic.py`) against real logged ownership: it under-estimated the top chalk by ~14 points (Bijan 4% est vs 43% real) while our own optimizer put him in 67-93% of lineups.
2. Built features: heuristic estimate (logit), the player's exposure across 60 optimizer lineups built with 25% projection noise (a proxy for the optimizing part of the field; 25% matched real ownership better than 10%), salary, top-priced-at-position flag, projection uncertainty (sigma/proj), dart flag (cheap RB/WR/TE), low-projection flag.
3. Logistic-scale ridge regression on real ownership, per slate; predictions renormalized to the position budgets (classic total = 900%) with a 75% cap via water-filling (a plain rescale pushed a few players to 96-100% on small slates).
4. Validated leave-one-WEEK-out (train on the other week, predict this one): chalk bias -14 -> -1.4 / -3.8; wk2 chalk MAE 15.0 -> 10.9; correlation 0.70 -> 0.85 (wk1 0.73 -> 0.77). Wk1 chalk MAE did not improve (small-slate hype misses).
5. Validated the "field" itself: an ownership-weighted simulated field built from ACTUAL ownership + actual player points reproduced the real field's score quantiles within ~2-7 points (Week 1 within ~2 after stretching spread by 1.10). This is how we scored lineup settings. Same idea can be built for showdown (1 CPT at 1.5x salary and points + 5 FLEX, cap $50,000).
6. Findings to keep in mind: accurate ownership does NOT make lineups better by itself (a flat ownership penalty in the optimizer hurt, even with perfect ownership); accuracy is for informed leverage decisions.

## 3. Showdown specifics that differ from classic
- Every player appears twice in the pool: a CPT row (1.5x salary, 1.5x points) and a FLEX row. Real ownership is separate for CPT and FLEX ("%Drafted" per Roster Position in DK's results export).
- Budgets: `compute_showdown_role_budgets()` in `ownership_heuristic.py`: CPT group 100% total, FLEX group 500% total. Heuristic entry points: `add_showdown_ownership_columns()` (build_projections.py), `build_showdown_role_group()`. Showdown currently has NO fitted model (it reuses the classic 5-feature chalk blend with the role grouping).
- Any position can go in any slot, incl. kickers and DSTs (kickers were very valuable last week). Two-team pool: team-split (5-1, 4-2, 3-3) and QB/pass-catcher/opponent correlation matter much more than in classic.
- Classic-only features do not transfer directly: "top-priced-at-position" and position budgets need redefining for CPT vs FLEX and K/DST.
- The projection stack (`projection_stack.py`) is skipped for Showdown (salary scale differs) and the layered ownership model is DK classic only. Showdown projections = engine + player-prop market anchor (`props_model.py`, default 0.5 blend when a fresh snapshot exists) + participation fix.
- Showdown optimizer functions (in `scripts/optimizer.py`): `solve_showdown_lineup`, `build_multi_showdown_lineup`, `load_showdown_pool`; CLI needs `--format showdown` (auto-detected from the pool), supports `--min-team-players TEAM:N`; `--min-total-ownership`/stack options are rejected for Showdown. To get an "optimizer exposure" feature for showdown, run `build_multi_showdown_lineup`-style solves in-process (the classic code used `optimizer.solve_lineup` + `randomize_projections`; the showdown equivalent is `solve_showdown_lineup`).
